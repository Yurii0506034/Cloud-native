# Лабораторна робота №5: Неблокуючий I/O у реальному часі: Node.js Streams, Backpressure та WebSockets

## 1. Мета роботи
Розширити серверний застосунок функціональністю неблокуючої потокової обробки великих масивів даних за допомогою **Node.js Streams** (`Readable`, `Transform`, `Writable`), дослідити механізм контролю зворотного тиску (**Backpressure**) при роботі з повільними споживачами, а також інтегрувати **WebSocket-сервер** для передачі прогресу обробки даних клієнтам у реальному часі.

## 2. Архітектура системи
Проєкт побудовано зі збереженням багаторівневої архітектури (Separation of Concerns), де HTTP API, потокова обробка та WebSocket-комунікація розділені на незалежні модулі:

```
              HTTP API
                  │
                  ▼
         Controller / Router
          ┌───────┴───────┐
          ▼               ▼
   Stream Service    WebSocket Server
          │               │
          ▼               ▼
Read → Transform → Write  Connected Clients
          │               │
          ▼               ▼
     Backpressure    Real-time events
```

## 3. Реалізація основних модулів

### 3.1. Генерація великого джерела даних (`src/generate-file.js`)
Для тестування потоків створено генератор NDJSON-файлу розміром **150.00 MB** (`1 522 325` рядків). Запис виконується через `fs.createWriteStream` із перевіркою результату `writeStream.write()` та очікуванням події `drain`, що запобігає переповненню оперативної пам'яті під час генерації.

### 3.2. Потокова обробка та Backpressure (`src/services/stream.service.js`)
- **Readable Stream**: `fs.createReadStream` читає файл порціями (розмір чанка задається параметром `highWaterMark`, за замовчуванням `64 KB` = `65536` байт).
- **Transform Stream**: Аналізує кожен фрагмент, коректно склеює розірвані на межі чанків рядки, підраховує загальну статистику та фільтрує лише записи зі статусом `"ERROR"`.
- **Writable Stream & `pipeline()`**: Записує відфільтровані записи у вихідний файл `processed-errors.ndjson`, автоматично керуючи паузами читання при заповненні буфера запису.

### 3.3. WebSocket-сервер та захист від повільних клієнтів (`src/ws/ws.server.js`)
- При підключенні кожного клієнта генерується унікальний `clientId`, фіксується час підключення `connectedAt` та стан з'єднання.
- Реалізовано обробку вхідних повідомлень, валідацію JSON-формату та розсилку (`broadcast`) подій прогресу всім активним підписникам.
- **Захист від Backpressure у WebSockets**: Перед відправленням кожного фрейму перевіряється властивість `ws.bufferedAmount`. Якщо обсяг невідправлених даних у буфері клієнта перевищує `1 MB`, застосовується стратегія **Message Dropping** (пропуск проміжних кадрів прогресу). При перевищенні критичного порогу `5 MB` сервер примусово закриває з'єднання (**Connection Termination**).

## 4. Результати експериментів та вимірювань

### 4.1. Метрики потокової обробки файлу (150.00 MB)
При запуску `POST /api/stream/process` з розміром чанка `64 KB`:
- **Розмір вхідного файлу:** `157 286 403` байт (`150.00 MB`)
- **Загальна кількість рядків:** `1 522 325`
- **Знайдено та записано помилок:** `76 116`
- **Загальний час обробки:** `835 мс`
- **Пікове споживання пам'яті (RSS):** `64.33 MB` (менше половини розміру оброблюваного файлу, що підтверджує відсутність завантаження всього файлу в RAM).

### 4.2. Порівняння сценаріїв Backpressure (`GET /api/stream/backpressure?delay=5&chunks=300`)
Для дослідження впливу повільного споживача проведено тест на 300 чанках (по 64 KB) із штучною затримкою обробки 5 мс на кожен чанк:

| Сценарій | Оброблено чанків | Час виконання (ms) | Пікова пам'ять RSS (MB) | Особливості поведінки |
| :--- | :---: | :---: | :---: | :--- |
| **Scenario A (No Backpressure)** | 300 | 93 ms | 81.38 MB | Потік читає всі дані миттєво без пауз, накопичуючи проміжні буфери та таймери в оперативній пам'яті. На великих обсягах це призводить до вичерпання пам'яті (OOM). |
| **Scenario B (With Backpressure)** | 300 | 4637 ms | 88.26 MB | Механізм `pipe()` призупиняє `Readable` потік після заповнення `highWaterMark` повільного `Writable` споживача, синхронізуючи швидкість читання зі швидкістю запису. |

### 4.3. Перевірка Real-Time інтеграції з WebSocket-клієнтом
Під час обробки файлу підключений клієнт (`clientId: b06774c4`) отримував повідомлення про прогрес у реальному часі без очікування завершення операції:

## 5. Висновки
1. Використання потокової обробки даних (`fs.createReadStream`, `Transform`, `fs.createWriteStream`) дозволяє обробляти файли великого обсягу (`150 MB` і більше) за менш ніж 1 секунду зі стабільно низьким споживанням оперативної пам'яті (~64 MB).
2. Механізм **Backpressure** є критично важливим при взаємодії швидкого джерела даних із повільним споживачем: без нього система ризикує вичерпати доступну пам'ять через неконтрольоване накопичення черги невідправлених буферів.
3. Інтеграція потоків із **WebSockets** та контроль `ws.bufferedAmount` забезпечують ефективну передачу подій прогресу клієнтам у реальному часі та захищають сервер від деградації продуктивності через повільні мережеві з'єднання.
