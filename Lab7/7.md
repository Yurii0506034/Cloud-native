# Лабораторна робота №7: Безстатусна безпека: JWT-автентифікація, хешування паролів, протидія ін’єкціям та захист артефактів збірки у Node.js

## 1. Мета роботи

Розширити серверні сервіси із попередніх лабораторних робіт безстатусною безпекою: замінити відкритий доступ автентифікацією та авторизацією на базі **JWT (JSON Web Tokens)**, додати криптографічне хешування паролів (**bcrypt**), централізовані захисні заголовки (**Helmet**), обмеження частоти запитів (**Rate Limiting**), протидію SQL/NoSQL ін’єкціям, автентифікацію **WebSocket-з’єднань** та захист артефактів збірки шляхом **обфускації**. Уся нова функціональність інтегрована через ланцюжок middleware-фільтрів без зміни бізнес-логіки рівнів `Service` та `Repository`.

## 2. Архітектура та ланцюжок безпеки

            │  • requireAuth (JWT verify)  │
            │  • requireRole (RBAC)        │
            └──────────────┬───────────────┘
                           │
                           ▼
                     ┌───────────┐

## 3. Реалізовані механізми захисту

### 3.1. Розширення схеми бази даних та хешування паролів

* У таблицю `users` PostgreSQL (`init.sql`) та документи MongoDB додано поля `password_hash` та `role` (за замовчуванням `'user'`).

* Для хешування паролів використано криптографічний алгоритм **bcrypt** з фактором складності `SALT_ROUNDS = 12`.

* Верифікація при вході виконується через `bcrypt.compare()`, що забезпечує порівняння за постійний час (*timing-safe*) і захищає від атак за часом виконання.

* Поле `password_hash` виключається на рівні формування DTO і **ніколи** не повертається в API-відповідях чи логах подій.

### 3.2. JWT-автентифікація та захист від підробки токенів

* **Access-токен**: термін життя 15 хвилин, підписується криптостійким 256-бітним секретом `JWT_SECRET`.

* **Refresh-токен**: термін життя 7 днів, підписується окремим секретом `JWT_REFRESH_SECRET`.

* У *claims* токенів зберігаються лише безпечні метадані: `sub` (ID користувача), `email`, `role`, `iss`.

* Під час верифікації явно вказується дозволений список алгоритмів (`algorithms: ['HS256']`), що унеможливлює атаку підміни заголовка з алгоритмом `alg=none`.

### 3.3. Політика контролю доступу (RBAC)

* **Публічні маршрути**: `POST /api/auth/register`, `POST /api/auth/login`, `POST /api/auth/refresh`, `GET /health`.

* **Автентифіковані маршрути (`requireAuth`)**: `GET /api/users`, `GET /api/users/:id`, `GET /api/events`, `GET /api/users/export`.

* **Адміністративні маршрути (`requireAuth` + `requireRole('admin')`)**: `POST /api/users`, `PUT /api/users/:id`, `DELETE /api/users/:id`.

### 3.4. Заголовки безпеки, Rate Limiting та протидія ін’єкціям

* **Заголовки безпеки (`Helmet`)**: централізовано встановлено `Content-Security-Policy`, `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Strict-Transport-Security`, `Referrer-Policy: no-referrer`.

* **Rate Limiting**: на ендпойнт `POST /api/auth/login` встановлено ліміт — не більше 5 невдалих спроб за 1 хвилину з однієї IP-адреси (далі повертається `429 Too Many Requests`).

* **Протидія SQL/NoSQL ін’єкціям та Prototype Pollution**:

  * У PostgreSQL застосовано виключно параметризовані запити (`$1`, `$2`).

  * У MongoDB вхідні параметри проходять перевірку типу (`typeof email === 'string'`) і приводяться до примітивного рядка (`String()`), що нейтралізує оператори на кшталт `{"$gt": ""}`.

  * Middleware `sanitizeBody` перевіряє власні ключі об'єкта (`Object.keys()`) на наявність `__proto__`, `constructor`, `prototype`.

### 3.5. Автентифікація WebSocket та події безпеки

* Під час WebSocket handshake сервер перевіряє токен із query-параметра `ws://localhost:3000/ws?token=<JWT>`.

* З'єднання без токена або з невалідним токеном відхиляється сервером із кодом закриття **1008 (Policy Violation)**.

* Усі події безпеки (`user_registered`, `user_logged_in`, `login_failed`, `token_rejected`) зберігаються в колекції `events` у MongoDB, а подія `user_registered` транслюється всім підключеним WS-клієнтам.

## 4. Результати тестування та перевірки

1. **Реєстрація (`POST /api/auth/register`):**
   Створено користувача `Alice Secure` (`alice@example.com`), повернено статус `201 Created`:

   ```
   id         : 1
   name       : Alice Secure
   email      : alice@example.com
   role       : user
   created_at : 2026-11-18T13:58:14.095Z
   
   ```

2. **Логін та отримання токенів (`POST /api/auth/login`):**
   Отримано пару токенів `accessToken` (JWT) та `refreshToken`.

3. **Перевірка RBAC (`POST /api/users` під роллю `user`):**
   При спробі створення нового користувача без прав адміністратора сервер повернув статус **`403 Forbidden`**.

4. **Перевірка протидії ін’єкціям:**

   * Запит з SQL-пейлоадом `"admin' --"` у полі `email` відхилено зі статусом **`401 Unauthorized`**.

   * Запит з NoSQL-пейлоадом `{"$gt": ""}` у полі `email` відхилено зі статусом **`401 Unauthorized`**.

## 5. Захист артефактів збірки (Обфускація)

За допомогою інструмента `javascript-obfuscator` виконано обфускацію вхідної точки сервера (`src/app.js` $\to$ `dist/app.js`) з увімкненням ускладнення потоку керування (`control-flow-flattening`), ін’єкції мертвого коду (`dead-code-injection`), базового кодування рядків (`base64`) та самозахисту (`self-defending`):

| Артефакт | Розмір (байти) | Опис | 
| ----- | ----- | ----- | 
| **`src/app.js`** (вихідний код) | `2 389 B` | Читабельний вихідний код сервера | 
| **`dist/app.js`** (обфускований) | `8 449 B` | Захищений артефакт збірки (збільшення розміру у \~3.5 раза) | 

Обфускований артефакт зберіг повну функціональну еквівалентність і успішно обслуговує HTTP та WebSocket запити.

## 6. Висновки

У ході лабораторної роботи успішно реалізовано комплексну систему безстатусної безпеки для розподіленого вебзастосунку. Впроваджено криптографічне хешування паролів, двотокенну JWT-автентифікацію (Access + Refresh), рольову модель доступу (RBAC), захисні HTTP-заголовки, обмеження частоти запитів проти brute-force, автентифікацію WebSocket-з'єднань та обфускацію артефакту збірки. Усі секретні ключі надійно ізольовано через `.env` та виключено з репозиторію за допомогою `.gitignore`.
